# Domain Trio Protocol - One Stack's Design, Build, Verify Vertical

The execution protocol for the single-stack modes (`domain_trio`, `fanout_domain_trio`). By the time this file is read, the scoping verdict has already named the stack - a user hint ('frontend only', 'just the API') pins it the same way. The seats are resolved from the installed roster by the naming pattern `<stack>-solution-designer` / `<stack>-implementer` / `<stack>-verifier` (the generated capabilities rule lists what this project actually has). Everything technology-specific - conventions, patterns, what a good design or a passing verify looks like - lives in the seats and the skills they load, never here.

DELEGATED vs INLINE is picked once, before DESIGN - the calling skill's run-start session-or-agents ask decides it (deep dive: `project-solve-cross-task`'s `references/execution-modes.md`, where installed): DELEGATED dispatches every seat; INLINE does the same three steps in-session - design, build the tasks in the designer's order, verify against the plan - each through its single-chat twin where installed (`project-solution-design`, `project-implementer`, `project-verify-code`; a twin inherits the recorded mode and never re-asks), so an inline plan carries the same card contract a dispatched designer's does - traps, anchors, `log_points`.

## Steps

1. **DESIGN** - dispatch the stack's solution designer with the clarified requirement (the clarify gate already ran in the skill body - never design against a guessed one). Check the returned decomposition for BALANCE and file boundaries before dispatching seats: a task card whose surface (entities/files touched) is a large multiple of its siblings gets re-split (measured: 2 of 7 one-task seats carried 67% of a run's implementer spend at 13-18x their siblings), and two cards sharing a build-colliding file run serial, never parallel (measured: a concurrent pair tripped a transient compile collision on a shared file), and a card missing one of its stamps - `implementer_model`, `anchors`, the acceptance criterion, `log_points` - is a scoped re-brief to the designer, never a fan-out. For a diagnosed bug the plan comes from the diagnosis instead (`project-solve-cross-task`'s `references/issue-investigation.md`, where installed). Either way the output shape is the same: the architecture or the proven root cause, the test strategy, and a decomposition of independent tasks with contracts (each task's boundary and what it hands off or depends on). Gate the returned plan before anything builds - invoke `project-verify-plan` (the Skill tool, never its passes replayed from memory) and run its four passes in-session, recording the four per-pass verdicts (`risk / scope / edges / soundness`) in the ledger; a failed pass is a scoped re-brief to the designer - then STOP: present the gated plan and put the review to the user via AskUserQuestion - approve-and-build vs changes-needed, free text via Other (plain-text options where the harness lacks the tool) - and build only on the approving answer, which is the explicit word the calling skill's plan review stop and any approval gate file quote verbatim. A blanket dispatch opt-in in the ask is NOT that word, and neither is a run-the-whole-flow or completion-token instruction - only an explicit review waiver ('run without plan review') skips the stop, recorded as `plan_review: waived` in the ledger. Never fan out against an unaudited, unreviewed, or unapproved plan. The receipt is the gate: BUILD does not start - dispatched OR inline - until the ledger carries `plan_review: approved - "<their words>"` (or the waived form); in DELEGATED mode write the approval gate file from those same words before the first implementer dispatch (the dispatch hook enforces the file; the ledger field is the gate INLINE mode has). A build step reached with that field absent is a protocol violation, headless runs included (measured: two headless runs built straight past this stop; the one dispatch attempted without the stamp was stopped only by the hook).
2. **BUILD (fan-out)** - dispatch one implementer per independent task, all in parallel, from the main session. Fan out every task the designer marked independent, not a token two - the runtime bounds real concurrency; your job is to expose all of it. Hand each implementer exactly one task plus its contract; it never touches anything outside its boundary, which is what keeps the parallel runs collision-free. Write context shared by several tasks ONCE - in the plan file or the serena handoff note - and point each brief at it instead of restating it per brief: brief authoring stays in the orchestrator's context permanently, and a measured 12-brief fan-out restating the same context carried ~64k of it. Shared context includes the CONSTANTS and surfaces several tasks program against - a config threshold, a shared fixture's exported symbols - so a dozen seats do not each re-read the same file for one value (measured: one config read 14x and one fixture ~90 ranged reads across seats). And the pointer each brief carries is a per-task SLICE - the task's own section as a line range, or its card in the handoff note - never the whole plan file's path: seats pointed at the plan each read all of it (measured: 7 whole-plan reads across 5 seats, ~71k tokens, for tasks that each needed one section). Dispatch each with the `implementer_model` the designer stamped on the task card, passed as the per-dispatch model override; the seat's frontmatter pin is the fallback when a card carries none (full rule: `project-solve-cross-task`'s `references/model-routing.md`, where installed - the card's stamp and the frontmatter fallback are the operative parts).
3. **VERIFY (fan-in)** - once every task lands, dispatch the stack's verifier over the assembled whole, never over a single task. This fan-in is a checked step: the round-close report names the verifier dispatch - or, in INLINE mode, the explicit self-verification it substituted - and a round that landed implementer work cannot close without one (measured: a 14h run landed ~30 substantial implementer tasks with zero verifier dispatches, leaving the same context that authored the plans to also gate them; the one regression avoided that run was caught by the designer step, not verification). On a punch-list, route each item back to the implementer that owns it, **resumed with a scoped brief** - the failing assertion or check plus the file and symbol to touch, not a fresh full-context re-brief (a full re-dispatch roughly doubles the cell's cost for a one-line fix) - then re-dispatch the verifier. The verifier's independent checks (build, the test suite, the contract-seam probe) are parallelizable - run them concurrently where the seat supports it. Loop until sign-off, but bound the loop: **two implementer fix rounds maximum**; still failing after that, stop and escalate to the user rather than looping to sign-off forever.

## Bookkeeping

- **Progress ledger.** The run's ledger is the same durable file `project-solve-cross-task`'s `references/agent-output-protocol.md` formats (where installed - a plain per-task status/verdict table serves without it) - every task and its status, each verify pass, and the contract_version when the run sits under a frozen cross-domain contract - so a mid-run compaction resumes without re-deriving what already landed.
- **File hand-off, per-task review.** Each implementer gets its task + contract as a written brief and returns a written report; glance at each task's diff the moment it returns - not after the whole fan-out, and not by serializing the implementers. The verifier still runs once over the assembled whole; the early glance only catches a contract breach before it compounds.
- **Status routing.** Route on each implementer's closing status: DONE -> hand to the verifier; DONE_WITH_CONCERNS -> carry the flag to the verifier; NEEDS_CONTEXT -> close the gap via the designer, then re-dispatch; BLOCKED -> sequence after the blocking task; BLOCKED_CONTRACT_CHANGE -> pause the affected work and run the contract-change protocol (`project-solve-cross-task`'s `references/contract-protocol.md`; absent it, pause the lane and put the change to the user). The routing lives here; the status definitions and structured shapes are that same skill's `references/agent-output-protocol.md`.
- **Seat death.** A seat killed mid-task by API errors (5xx / overloaded) is re-dispatched with a scoped resume brief - its handoff note and partial diff name what already landed, the brief carries only the remainder - never finished inline by the orchestrator (measured: four implementers died in one outage window and their tests, finished in the main session instead, pulled build work into a ~380k-ctx context). A death re-dispatch resumes the same round - it never consumes a verify fix round; when no handoff note was written yet, the partial diff alone scopes the resume. Deaths cluster in outage windows - re-dispatch after a short pause, not instantly.
- **Memory hygiene.** The serena handoff notes live in the gitignored `.serena/memories/` and outlive a branch switch. ONE naming grammar: `<feature>__<contract_version>__<seat>` for a single-note seat (designer, verifier, diagnoser), with a trailing `__<task>` segment for implementers (one note per task) - and the ORCHESTRATOR mints `<contract_version>` and puts each seat's literal note name in its dispatch brief, verbatim; a seat never derives its own name from the pattern (measured across three projects: seats handed only the pattern produced 3-5 incompatible schemes per run - feature and version swapped, literal `contract_version` text baked into names - and one read failed on a guessed name). A seat reads only the notes matching its `<feature>__<contract_version>`, never a stale one. After the verifier signs off, purge the run's notes (serena `delete_memory` on each `<feature>__*`) so they never bleed into a later run that reuses the workspace - and the round-close report carries the receipt, `memories purged: <names|none>`, as a REQUIRED field the close is incomplete without - and a close whose deletes trail the run's writes is incomplete even with the field present (measured: one run wrote 27 notes and deleted zero, a second wrote 28 and deleted zero, and two projects accumulated 79 and 55 stale notes - a purge instruction with no report field is skipped every time). The purge is FOLD-FIRST: before deleting, anything in a note that outlives the run - a flagged-but-unfixed bug, an owed gate, a decision the close must report - is folded into the ledger/task docs or the close report; an unconditional purge once destroyed the sole record of a flagged bug (measured). An `rm` of the note files is the same purge (`.serena/memories/` is plain files) - it satisfies the receipt identically; what matters is fold-first, then delete, then the receipt names what went.

## Rules

- The main session is the only orchestrator for the whole vertical. The domain seats carry no Agent tool - the fan-out stays flat, and no seat is ever told to dispatch another.
- **Seat gates are fast.** An implementer's green gate is the stack's build plus the relevant fast tests only - never a minutes-long verification (an integration/replay suite, an E2E pass) in any seat's dispatch brief. A dispatched seat cannot cheaply wait on one: measured, it idles on the run, spawns overlapping background monitors, and burns about half its cost on wake-up churn without ever delivering its report. The slow, full verification runs ONCE over the assembled whole, owned by the main session after fan-in - never delegated into a seat, the verifier included. Coverage measurement is not a build gate at all - it runs on its own deliberate cadence via the `project-test-coverage-analyzer` capture.
- **On-demand skills can be absent.** A seat's frontmatter preloads always install with the seat; the skills a brief tells it to load on demand are per-project - narrow specialists that arrive only where the project's stack or evidence shows the area. So load one only when it is in your skill list, and when a name is not there the project has no such surface: work from the preloaded conventions and never call an absent skill (the call fails 'Unknown skill' and the seat burns the turn absorbing it).
- Fan out only the tasks the designer marked independent, and respect the contracts it drew between them - two implementers touching the same boundary is the collision the contracts exist to prevent.
- The architecture docs are not refreshed by this flow. The fit verdict (extend / refactor first / isolate) is the designer's call from the committed map; reconciling the docs after a structural change is a deliberate capture run (`project-architecture-analyzer` / `project-architecture-quality-loop`), never a step here.
